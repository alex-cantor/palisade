# Palisade: A Brief Overview (part 1)

## Initial Ideation

Ask any CCDC competitor the best way to get good (like [hypernova](https://akshayrohatgi.com/blog/posts/How-To-Win-CCDC/#time-travel), and their answer will likely be the same: get experience. It is really hard to do this through only competitions, as there are only a couple of competitions per year. The best way is through mock competitions, so I knew I wanted to build infrastructure to spin up mock competitions *fast*.

I also knew I wanted to have the environment replicate CCDC environments as best as possible. Originally, I was going to provision credentials for my teammates to access the infra directly on ProxMox, but one of my teammates (@lolmenow) told me about a portal he was building to replicate eCitadel--which runs in an environment very similar to CCDC. I thought this was an awesome idea, so a component of palisade will be said interface (which we’ll discuss in depth later). More broadly, for the project, I thought it would be best for there to be three general components: the mock environment generator itself, the CCDC-like interface, and the autonomous red teamer. We’ll discuss each in greater depth later.

Due to the nature of this project (and CCDC itself), I am also excited for potential applications outside of CCDC. In volunteering with the Iowa Air National Guard, I was tasked with helping to configure, deploy, and pentest a vulnerable network for them to then watch logs. By being able to spin up a network as I will eventually be able to do with palisade, this task will become trivial. In addition to the defensive side, networks could be spun up for practice with red teaming and pentesting.

> Disclosure: I already have access to a ProxMox (PVE) server with root permissions and a ton of resources (70TB of usable storage plus ½ PB sitting, waiting to be plugged in, so I am starting off at a better point than most competitors. That said, you should be able to replicate this project via a service like Hetzner or OVHCloud for less than $100/month.

## Initial Guidelines

As I began to work on the project early on, I wanted to establish a set of guidelines:
1. This project must remain in a specific Resource Pool I created--I did not want to deal with the consequences of nuking my old high school’s network.
2. Building on the previous point, I restricted the generated VM range to the 5000s and the VM templates to the VMID 9000s range. Of course, similar to the previous version, I wanted to ensure I didn’t collide with the other network. In addition to this, I wanted to have a bit of organization in what I was doing. As such, in addition to the 5000 and 9000 ranges, I grouped VMs by a few different means (OS, distro, etc).
3. Ok, I promise this is the last “building on” point--but organization was super important. Tags. I love PVE tags. I knew I wanted to use tags for labeling details about each VM, for grouping between competitions, for grouping between teams, etc.
4. I wanted the vulnerabilities and scenarios to be pulled from a very large, AI-generated pool. I was originally thinking it would be cool if the vulnerabilities were generated on the fly, but I quickly ditched that idea (as AI is non-deterministic, I didn’t want to worry about potential issues; plus, this way I have additional control overall)
5. I think this counts as a different “building on”? Not only did I want the vulns and scenarios to be pulled, but I wanted the distros to be pulled. And, I wanted my team to be prepared for anything, so I grabbed some weird and old operating systems (there is one I have not yet touched and don’t really want to grab--can you guess what it is?)
6. I really didn’t want to deal with vlanning (if you didn’t know it already, I am *not* a networking guy), so I kept everything on the same LAN. Whether or not this is a good idea, I don’t know--and I may change it in the future, but this is what I have at the moment.

## Building the Mock Environment Generator

As I began thinking through the project, I quickly realized the high level architecture was quite simple. When the tool is launched, based on a few parameters which could be set, it would grab the VMs, vulnerabilities, and scenario from a very large preset (generated by AI) catalog, which then provisions the VMs with those vulnerabilities.



Functionally, none of these steps are difficult. The execute step simply involves running the script. The randomization of the environment step simply involves a call to a random library and selecting a few options (there is a bit nuance here, which I’ll discuss later), and the provision step, which leverages relatively simple commands to provision the VMs from templates, add the vulnerabilities to the VMs, and provision new competitor accounts for users.

I’ll go into detail on each of these steps at a later time.

> Of note, it will be possible to generate networks without preset vulnerabilities (minus default credentials) so competition organizers can implement their own vulnerabilities.

## Building the CCDC-like Interface

Thanks to @lolmenow (here is where he is building it: https://portal.sakouk.me/login), I knew I wanted to build it with Apache Guacamole. I thought a good bit about how I wanted to build the architecture, so I decided on the following:
1. Users could login at https://portal.acantor.me/login, but would not be able to register. Competition organizers, who receive credentials via the system administrator (me), would be able to provision users
2. Once authenticated, there would be 5 options: Scoreboard, Injects, Announcements, Services, and VMs. The Scoreboard page would display the scores of each team, broken down by category. The Injects page would display pending and completed injects, as well as scores and feedback for each inject. Announcements would be any announcements, Services would be the up and down services across each service and team, and the VMs page would enable teams to start/stop, snapshot, revert, or use the VM in the browser.

## Building the Autonomous Red Teamer

My initial thoughts are that I’ll configure the autonomous red teamer to run enumeration but ultimately have access to the vulnerabilities on the system and, at select times, exploit the vulnerabilities. That way, it is fair for all teams. The enumeration would strictly be so blue teams have experience seeing it.
